# explain — 사용자가 읽고 이해하거나 정할 수 있게 쓴다

## 왜 따로 있나
이 상황에서는 사람이 Codex 가 만든 것을 이해하고, 판단을 내리고, 끝나면 AI 없이 설명해야 한다 (SITUATION.md 의 인지 축과 후속 문항). 설명이 일반적이면 읽는 사람의 높이와 어긋나서 읽히지 않는다. 그래서 읽는 사람(PROFILE.md)에 맞춘 모양 셋을 고정한다.

## 입력과 출력
| op | 입력 | 출력 |
|---|---|---|
| understand | 설명할 대상(파일, 코드 범위, 개념, 동작)과 질문 한 줄 | 답, 뼈대, 그림, 실제 값 따라가기, 부품 표, 왜, 더 팔 곳 |
| decide | 정할 일, 근거가 될 파일과 명령 결과, 담당자 답 | 결론, 정할 것과 추천, 그림, 비교 표, 근거, 모르는 것 |
| prep | 지금까지의 docs/ 와 코드, git log | docs/reports/prep.md: 사용자가 AI 없이 말할 구조, 결정, 약점, 예상 질문 |

- 대상을 먼저 읽는다. 읽지 않은 것은 설명하지 않는다.
- 30줄 이하는 터미널에 쓴다. 넘으면 docs/reports/<HHMM>-<주제>.md 에 쓰고 터미널에는 경로와 결론 한 줄만 쓴다 (터미널은 읽는 자리가 아니고, 에디터의 Markdown 미리보기가 읽는 자리다). 파일 길이 상한은 150줄이다.
- op 를 시작하기 전에 ops/<op>.md 를 읽는다. docs/context.md 가 있으면 함께 읽는다 (setup fill 이 쓴 이번 과제 칸). 파일로 쓴 경우 docs/state.md 진행 표에 한 줄을 남긴다.

## 문장 규칙 (모든 op)
- 한 문장에 사실 하나. 모든 문장에 동사.
- "·" 나 "→" 로 이은 조각 줄을 쓰지 않는다. 화살표는 그림 안에서만 쓴다.
- 새 낱말은 쓰기 전에 괄호로 푼다. 비유를 먼저, 공식 용어를 다음에 쓴다. 비유는 references/anchors.md 에서 고른다.
- 코드를 보일 때는 첫 줄에 출처(파일:줄, 또는 라이브러리 이름)를 쓴다.
- 꼭 읽을 줄 앞에 ★. 세 개까지.
- 요약 위의 요약, 칭찬, 다짐, 맺음말, 끝의 복습 질문을 쓰지 않는다.
- PROFILE.md 이해도 표에서 "강함" 인 영역은 설명하지 않고 비유의 기준으로만 쓴다.

## 자유도
ops 의 칸과 순서는 기준선이다. 대상에 더 맞으면 칸을 합치거나 더하거나 순서를 바꿔도 된다. 바꾼 것은 답 끝에 한 줄로 적는다. 바꾸지 않는 것: 맨 위의 결론(또는 답)과 정할 것, 출처 표시, 읽지 않은 것을 설명하지 않기. understand 의 뼈대 칸.
