# research — 모르는 것을 짧게 익히고, 확인할 질문으로 바꾼다

## 왜 따로 있나
이 상황의 파트너는 해결 방법을 알려 주지 않는다. 도메인 지식은 AI 로 익히고 파트너에게 확인하는 과정 자체가 평가된다 (SITUATION.md). 그래서 조사는 답으로 끝나지 않고, 파트너에게 던질 확인 질문으로 끝난다. 기술 조사는 사용자가 설명할 수 있는 쪽을 고르게 돕는다.

## 입력과 출력
| op | 입력 | 출력 |
|---|---|---|
| domain | README, docs/questions.md 의 답, 자료 파일, 조사 질문 한 줄 | 현업 방식 요약, 영역 지도, 용어, 방식 후보와 확인 질문, 자료 실측 |
| tech | 만들 기능 한 줄, plan.md 스택 칸 | 후보 비교 표, 추천 하나, 가장 작은 사용 예 |

- 답은 explain 스킬의 decide 모양으로 쓴다. 30줄을 넘으면 docs/reports/<HHMM>-research-<주제>.md 에 쓴다.
- op 를 시작하기 전에 ops/<op>.md 를 읽는다. docs/context.md 가 있으면 함께 읽는다 (setup fill 이 쓴 이번 과제 칸). 끝나면 docs/state.md 진행 표에 한 줄을 남긴다.
- 답 하나로 끝낸다. 더 필요하면 다음 조사 질문 하나를 제안하고 멈춘다.

## 출처 규칙
references/sources.md 를 따른다. 짧게는 이렇다.
- 출처는 넷이다: 파트너 답(Q#), 작업 폴더의 파일, 웹(검색이 되면 URL), 모델 지식.
- 주장마다 출처를 붙인다. 모델 지식과 웹은 파트너가 확인하기 전까지 추정이므로 줄 끝에 "(확인 전)" 을 붙인다.
- 믿을 만한가와 이 과제에 쓸모 있나는 따로 판단한다.

## 읽는 사람
PROFILE.md 이해도 표에서 이미 아는 영역은 조사하지 않는다.

## 자유도
ops 의 칸과 순서는 기준선이다. 대상에 더 맞으면 칸을 합치거나 더하거나 순서를 바꿔도 된다. 바꾼 것은 답 끝에 한 줄로 적는다. 바꾸지 않는 것: 맨 위의 결론(또는 답)과 정할 것, 출처 표시, 읽지 않은 것을 설명하지 않기. 모델 지식에 "(확인 전)" 붙이기.
