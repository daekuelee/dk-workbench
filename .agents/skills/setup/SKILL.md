# setup — 질문과 근거로 이번 과제의 출발점을 맞춘다

read로 초기 이해·자료 특성·풀어야 할 질문을 드러낸다. 사용자는 이해를 고치고, 필요한 질문을 직접 전달하거나 자료 확인을 요청한다. fill은 받은 답과 선택을 반영하고 출발할 만큼 준비됐는지 판단한다. 질문을 다 소진하거나 설계를 전부 확정하는 과정은 아니다.

## op
| op | 입력 | 남기는 것 | 끝나는 곳 |
|---|---|---|---|
| read | README, 제공 자료의 대표 내용, 기존 기록, 확인 가능한 환경 | setup의 초기 이해·자료 특성, questions의 질문 후보, state | 이해와 질문의 이유를 보여 주고 사용자 수정을 기다린다 |
| fill | 사용자 확인·선택, 질문·답 원문 또는 원문 파일 경로 | 필요한 기록의 갱신, 준비도와 남은 쟁점 | 준비 완료 또는 추가 확인이 필요한 이유를 보고한다 |
| status | docs/state.md | 현재 위치와 다음 후보 | 답만 한다. 다음 작업을 실행하지 않는다 |

`read`는 기존 단일 세션 방식이다. 선택적으로 두 터미널에 나눌 수 있다.
- `read main`: [ops/read.md](ops/read.md)의 main 모드. README와 초기 업무 이해·질문·환경·공식 기록을 맡고 자료 보고를 기다리느라 사용자 인계를 늦추지 않는다.
- `read files` (`read file`도 같은 뜻): [ops/read-files.md](ops/read-files.md). 자료의 관찰·출처·한계만 반환한다. 메인 문서와 질문·답 원문을 쓰지 않는다.
- 같은 과제 폴더의 `setup-parallel.sh main`을 먼저, 다른 터미널에서 `setup-parallel.sh files`를 실행하면 분담과 자료 보고 경로가 연결된다. 모델·effort는 인자로 지정하거나 현재 환경 설정을 따른다. 병렬 실행은 의무가 아니며 코딩 절차를 고정하지 않는다.

read와 fill 전에 해당 ops 파일을 끝까지 읽는다. read만 요청했다면 fill로 넘어가지 않는다. 명확한 확인을 다시 요구하지 않는다. fill에서 부족한 부분이 나와도 read부터 재시작하지 않고 기존 이해와 받은 답을 이어 쓴다. 파트너 질문 전달과 다음 작업은 사용자가 한다.

## 준비도와 완료 기준
setup의 중심은 문제정의다. 완료 시 문제정의, 현재 업무와 중요한 기준, 이번 해결 범위·제외 범위, 성공 판단과 근거, 남은 미확인과 다음 행동을 함께 설명할 수 있어야 한다. 각 내용은 기존 기록을 연결하며 별도 문서를 늘리지 않는다. 합의한 문제정의의 원본은 plan 맨 앞의 짧은 문단에 둔다. 준비도 점수는 이 이해와 합의를 설명하는 보조 지표다.
기본 목표는 **85/100점**이다. 정답률이나 실측 지표가 아니라, 다음 행동을 정할 준비가 됐는지를 설명하는 판단 척도다. read는 잠정 평가, fill은 새 근거로 갱신한다. 점수의 원본과 근거는 docs/setup.md에 둔다.

| 항목 (각 20점) | 평가할 내용 |
|---|---|
| 문제·업무 이해 | 누가 어떤 상황에서 무엇 때문에 어려운가 |
| 범위·제약 | 이번에 개선할 것, 제외할 것, 중요한 제약이 구분되는가 |
| 성공 판단 | 도움이 됐는지 판단할 행동·결과·사례와 출처가 있는가 |
| 자료·환경 이해 | 자료의 내용·활용 가능성·한계, 필요한 도구와 환경의 확인 상태를 아는가 |
| 다음 행동·미확인 관리 | 다음 행동이 구체적이고, 남은 미확인의 확인 시점·방법 또는 제외 이유가 있는가 |

- 항목별로 0(근거 없음), 5(추측 수준), 10(부분 확인), 15(다음 판단에 충분하나 보완 필요), 20(필요한 근거로 명확함)을 사용한다. 각 점수에 근거와 남은 빈 곳을 짧게 붙인다. 문서 길이·질문 수·스택 확정 여부로 점수를 주지 않는다. 자료가 없는 과제는 자료 불필요 여부와 필요한 입력을 확인했는지 본다.
- **85점 이상 + 출발을 뒤집을 미확인 없음 + 출발점에 대한 사용자 확인**이면 setup 완료다. 명확한 fill 요청에 이미 담긴 확인을 다시 받지 않는다. AI가 새 범위나 설계를 제안한 것만으로 합의됐다고 쓰지 않는다.
- 80점대 초반이면 목표까지 남은 가장 중요한 확인을 보여 준다. 85점 이상이면 점수만 올리려고 질문을 늘리지 않는다. 사용자가 남은 위험을 알고 일찍 마치기를 선택하면 점수를 올려 꾸미지 않고 예외 종료와 이유를 기록한다.
- 점수와 별개로 대상·핵심 기능·범위·실현 가능성을 뒤집을 모순이나 미확인이 있으면 알린다. 확인하거나, 범위를 바꾸거나, 사용자가 영향과 검증 방법을 알고 가정으로 받아들여야 한다. 단순한 답 수신을 해결로 취급하지 않는다.
- 업무 기준이 README나 자료에 충분히 명시돼 있으면 파트너 질문을 의무화하지 않는다. 스택과 상세 설계는 지금 다음 행동에 필요한 만큼만 정한다. setup 완료는 구현 승인이 아니다.

## 경계와 필요한 파일
- 사실·자료에서 관찰한 것·AI 해석·사용자 선택을 구분한다. 출처를 붙이고 선택 이유를 만들어 쓰지 않는다.
- 코드 작성·패키지 설치·앱 실행은 하지 않는다. 키 값은 출력하지 않는다. 웹 검색·원문 가져오기는 사용자 허락 없이 하지 않는다. 필요하면 research의 출처 판단을 따른다.
- 대표 자료를 이해하는 읽기는 read에 포함한다. 전수 분석·도메인 조사·기술 비교는 현재 질문에 필요할 때 별도로 제안한다. 유형표·고정 질문 개수·전체 구현 계단을 강제하지 않는다.
- [ops/read.md](ops/read.md), [ops/fill.md](ops/fill.md): 실제 수행과 기록 방식.
- [templates/setup.md](templates/setup.md), [templates/example-setup.md](templates/example-setup.md): 보고 틀과 다른 과제의 견본. 분량과 내용을 복제하지 않는다.
- [references/question-ladder.md](references/question-ladder.md): 질문 후보를 만들거나 받은 답을 검토할 때.
- [references/archetypes.md](references/archetypes.md): 설계 후보가 필요할 때만. [references/rulings.md](references/rulings.md)는 과거 판정이며 현재 행동은 SKILL과 ops를 따른다.

사용자에게 보여 주는 설명과 새 기록은 한국어로 쓰고 인용 원문의 언어는 보존한다. 설명은 PROFILE.md에 맞춘다. 상세한 설명이 필요하면 explain을 쓴다. 메인은 완료한 op와 setup 전체의 완료 여부를 state에 구분해 기록한다. files 담당은 별도 자료 보고만 남긴다. 읽기 전용 실행에서는 실행기가 저장하며 직접 호출의 저장 경계는 read-files를 따른다. 설치는 install.sh가 맡는다.
