# setup read — 초기 이해와 풀어야 할 질문을 만든다

## 1. 안내와 자료를 읽고 업무의 윤곽을 드러낸다
- SITUATION.md와 PROFILE.md로 상황과 설명 수준을 확인한다. README의 목표 원문·제약·마감·실행 지침을 출처와 함께 읽는다.
- 기존 state·setup·context·questions와 관련 합의가 있으면 재사용한다. 이미 받은 답을 다시 묻거나 기존 요구·설계를 초기화하지 않는다. 필요한 파일을 찾았으면 서로 의존하지 않는 읽기·환경 확인은 가능한 범위에서 묶어 실행한다. 빈 문서 틀이나 같은 안내를 여러 번 읽지 않는다.
- 먼저 파일 목록·대략적인 크기·형식을 보고 관련 자료와 읽는 방법을 고른다. 저장소 메타데이터·의존성·생성물까지 재귀적으로 훑지 않는다. 확장자만으로 내용을 단정하지 않고 필요한 파일의 실제 형식과 인코딩을 가볍게 확인한다. 파일명·CSV·Python 등 특정 과제의 형식이나 도구를 전제하지 않는다.
- 텍스트·코드는 제목·관련 구간과 검색을, 표는 열과 서로 다른 내용의 표본을, 문서·이미지는 현재 환경의 지원되는 읽기 도구를 이용한다. 큰 자료를 통째로 출력하지 않는다. 지원하지 않는 형식은 읽지 못한 범위와 영향을 알리고 필요한 대안을 제안한다. 읽기만을 위해 패키지를 자동 설치하거나 프로젝트 언어·프레임워크를 세팅하지 않는다.
- 파일 목록과 헤더에서 멈추지 않는다. 과제와 관련된 자료별로 대표 본문을 읽어 무엇을 기록한 자료인지, 내용·형식의 차이, 자료끼리의 연결, 활용 가능성과 한계를 파악한다. 짧은 자료는 전체를 읽어도 되며 큰 자료는 목적에 맞는 일부를 본다. 첫 몇 행이 전체를 대표한다고 단정하지 않는다.
- 관찰한 차이나 모순 때문에 초기 이해가 달라질 때만 필요한 부분을 더 확인한다. 읽은 범위와 관찰 근거를 남기고, 일부 표본에서 전체의 빈도·품질·공식 업무 기준을 단정하지 않는다. 질문 생성에 충분하면 멈추며 전수 집계나 파일마다 일률적인 실측을 하지 않는다.
- 현재 이해한 사용자 → 업무 흐름 → 어려움 → 요청 결과를 먼저 짧게 보여 준다. 자료에서 보이는 사실과 AI 해석·모르는 것을 구분한다. README와 대표 자료로 초기 이해가 생기면 전체 문서 작성이 끝나기 전에 잠정 이해와 가장 중요한 질문·이유를 사용자에게 전달한다. 사용자는 이해를 고치거나 질문을 전달할 수 있고, AI는 이미 요청된 독립적인 확인·기록을 이어간다. 사용자 답에 달린 판단을 먼저 확정하지 않는다.

## 2. 필요한 환경을 확인한다
준비에 영향을 주는 항목만 읽기 명령으로 확인한다. 설치나 앱 실행은 하지 않는다.
- README의 실행 언어·도구가 있으면 버전과 사용 가능 여부를 확인한다. 예: `python3 --version`, `node --version`. 언어가 미정이면 사용 가능한 언어만 적고 스택을 고르지 않는다.
- 지정된 패키지·제공된 AI 호출 도구가 있으면 위치와 사용법을 확인한다. 단지 나중에 쓸 수 있다는 이유로 패키지 후보를 모두 조사하지 않는다.
- 앱 안 AI가 필요한 과제면 제공 지침·도구를 먼저 본다. 환경 변수는 이름과 존재 여부만 확인한다. 예: `python3 -c "import os; print('\n'.join(k+'=<값 있음>' for k in os.environ if any(s in k.lower() for s in ('openai','anthropic','api_key','llm','model'))))"`. 값과 인증 파일 내용은 출력하지 않는다.
- Codex 버전은 `codex --version`으로 확인할 수 있다. 현재 모델·effort, 승인·샌드박스, 적용된 지침 경로는 세션에서 확인 가능한 정보만 적는다. 설치된 모델 목록을 추측하거나 설정 파일 전체를 덤프하지 않는다.
- 필요한 포트가 명시돼 있으면 사용 여부를 확인한다. 실행 명령·포트·경로가 아직 없으면 미정이다.
- 권한 때문에 확인하지 못한 것과 실제 미설치를 구분한다. 작업을 막는 환경 미확인은 Helper에게 물을 질문으로 남긴다. 환경 답을 기다려야 하는 항목 외에는 준비를 마친다.


## 3. 질문 후보와 이유를 만든다
[../references/question-ladder.md](../references/question-ladder.md)를 참고한다. 사용자가 질문을 떠올리기를 기다리지 말고 README·자료에서 드러난 쟁점과 빠진 관점을 제안한다.
- docs/questions.md의 사용자 입력 영역에 Q별 질문·왜 묻는지·확인 대상과 근거를 미리 채우고, 각 질문 바로 아래에 빈 `답변:`과 선택적인 `내 메모:` 칸을 둔다. 먼저 확인할 질문과 답을 보고 이어갈 질문을 나눠 보여 준다. 아래 AI 영역은 Q별 상태·해석·반영 연결만 관리하며 질문을 중복 복제하지 않는다. 기존 사용자 원문과 Q#는 보존한다.
- 파트너에게 물을 업무 사실, 사용자와 정할 범위·설계, 로컬 자료에서 확인할 것, Helper에게 물을 환경을 구분한다. 파트너에게 언어·프레임워크 선택이나 해결 방법을 대신 정해 달라고 하지 않는다.
- 자료에서 이미 답을 찾은 것은 질문에서 제외한다. AI의 일반 지식은 질문을 만드는 가설로만 쓰고 해당 팀의 사실로 단정하지 않는다.
- 질문의 우선순위는 업무의 큰 흐름·핵심 어려움, 이번 범위·성공 기준에 주는 영향으로 판단한다. 자료의 특이점이 구체적이라는 이유만으로 첫 질문을 차지하지 않게 한다. 파일별 세부 규칙·예외는 그 답이 지금 방향을 바꾸거나 이미 고른 범위에 필요할 때 확인한다. 큰 흐름을 사용자에게 설명하는 것과 파트너에게 넓은 질문을 한꺼번에 보내는 것은 구분한다. 파트너에게는 핵심 빈 곳 하나를 구체적으로 묻는다. 이미 큰 방향이 확인됐다면 다시 묻지 않는다.
- 사용자의 별도 질문도 같은 장부로 받는다. 답에 따라 미답 후보를 조정하되 사용자가 적은 원문과 기존 답의 연결을 보존한다. 질문 수와 설계 순서를 고정하지 않는다.

## 4. 보고하고 멈춘다
- [../templates/setup.md](../templates/setup.md)를 참고해 docs/setup.md에 초기 이해·자료 특성·환경·준비도를 기록한다. 질문 원본은 questions에 두고 연결한다. SKILL의 85점 기준으로 현재 근거를 평가하되 아직 사용자와 맞추지 않은 해석은 확정된 것으로 채점하지 않는다.
- 채팅에는 ① 현재 이해 ② 자료에서 알게 된 특성과 한계 ③ 주요 질문 후보와 이유 ④ 준비도와 가장 중요한 빈 곳 ⑤ 사용자가 지금 할 일을 읽기 쉽게 보여 준다. 고정 분량에 맞추거나 긴 환경 표로 핵심을 묻지 않는다.
- 사용자는 초기 이해를 고치고, 필요한 질문을 전달한 뒤 questions의 해당 Q 아래 `답변:`에 원문을 붙이면 된다고 안내한다. 독자 질문·추가 대화는 자유 입력 칸이나 채팅·다른 로컬 파일로 받아 연결한다. 질문 번호나 표 작성을 요구하지 않으며, 답을 여러 개 모아 fill로 반영해도 된다.
- state에 read 완료와 setup 진행 중을 구분해 남긴다. 파트너 질문이 필요하면 전달할 첫 질문을 보여 준다. 마지막에는 현재 가장 필요한 다음 요청 하나만 제안한다. 업무 이해가 아직 틀릴 수 있으면 이해 확인을, 답을 모았다면 fill을 제안한다. 자동으로 fill이나 심화 조사에 넘어가지 않는다.
