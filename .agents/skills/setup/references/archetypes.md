# 문제 유형과 아키텍처 안

언어는 Python 을 먼저 고른다. 사용자가 읽을 수 있어야 diff 를 읽고 후속 문항에서 설명할 수 있다. pip 설치가 막히면 표준 라이브러리 안으로 간다. 화면은 HTML 한 장에서 시작한다. 프레임워크(React 등)는 사용자가 원할 때만 쓴다.

## A. 자료를 보여 주는 웹
- 신호: 자료 파일이 있다. "한눈에", "현황", "보고 싶다", "정리해서 보여 줘".
- 1안: FastAPI + HTML 한 장(fetch). 자료는 서버 시작 때 메모리로 읽는다.
- 2안: 표준 라이브러리 http.server + 서버에서 만든 HTML.
- 계단: S0 실측 → S1 숫자 하나를 화면에 → S2 파트너 기준의 핵심 집계 → S3 화면 구성(파트너 장면에 맞게).
- 검증: S0 에서 직접 집계한 값과 API 값을 verify.sh 로 비교한다.
- 함정: 날짜 형식, 대소문자, 중복, 빈칸, 기준일(오늘), 시간대.
- 이 유형에서 자주 숨는 것: 기준(무엇을 문제로 보나), 묶는 단위(사람, 팀, 기간), 보는 장면(회의 전, 휴대폰).

## B. 방식을 담은 AI 기능 서비스
- 신호: "연습", "코칭", "피드백", "돌아보기", "검수", "방식을 담고 싶다".
- 1안: FastAPI + HTML 한 장 + llm.py 한 파일(외부 호출은 이 한 곳) + 기록은 JSON 파일.
- 2안: 같은 구조에서 AI 대신 규칙 검사로 먼저 돌리고, AI 는 마지막 계단에 붙인다.
- 계단: S0 실측과 앱 안 AI 수단 확인 → S1 입력과 저장만 → S2 파트너 방식을 규칙이나 프롬프트로 → S3 돌아보기 화면, 바뀐 요구.
- 검증: 파트너가 준 잘한 예와 못한 예를 E# 케이스로 쓴다. 구조(필드, 길이, 금지 표현)는 스크립트로, 품질은 케이스마다 맞음/어긋남과 이유로 본다.
- 함정: 점수 매기기, 모범 답을 통째로 주기, 개인정보를 AI 에 그대로 보냄, 앱 안에서 쓸 AI API 가 있는지 모름.
- 이 유형에서 자주 숨는 것: 파트너가 무엇을 보고 판단하나(기준 여러 개, 한 번에 하나씩 나옴), 피드백의 말투와 양, 기록을 누가 보나.

## C. 분석과 보고
- 신호: "왜 그런지", "원인", "정리해서 알려 달라", 화면 요구가 약하다.
- 1안: Python 스크립트 + 결과를 HTML 한 장으로 보여 주는 작은 서버.
- 2안: 스크립트 + Markdown 보고.
- 계단: S0 실측 → S1 질문 하나에 숫자 하나 → S2 비교와 그림 → S3 결론과 한계.
- 검증: 수치마다 재현 명령을 붙인다.
- 함정: 상관을 원인으로 씀, 기준일, 표본이 작음.

## D. 업무 도구와 자동화
- 신호: "매번 손으로", "반복", "변환", "모아서", "보내기".
- 1안: CLI 스크립트 + 얇은 웹 화면(업로드와 결과 보기).
- 2안: CLI 만.
- 계단: S0 입력 예시 수집 → S1 한 건 변환 → S2 여러 건과 실패 처리 → S3 화면.
- 검증: 입력 예시와 기대 출력 파일을 비교한다.
- 함정: 실패한 입력 처리, 되돌리기, 같은 입력 두 번.

## 모든 유형에 공통
- 서버는 0.0.0.0 에 바인딩하고, 포트와 경로를 README 실행 방법과 state.md 에 적는다.
- 첫 동작본(S1)은 작업 시간의 1/3 안에 브라우저에 뜨게 한다.
- 화면은 실제 사용자의 장면(누가, 언제, 어떤 기기)에 맞춘다. 장면은 파트너에게 묻는다.
