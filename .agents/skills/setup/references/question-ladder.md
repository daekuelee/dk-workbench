# 질문 후보를 만들고 받은 답을 판단하는 법

## 질문은 현재 이해에서 나온다
README·대표 자료·이미 받은 답으로 업무의 윤곽을 먼저 보여 준다. 사용자가 질문을 다 떠올리기를 기다리지 않고, 관찰된 차이·모순·한계와 빠진 관점을 후보로 제안한다. 질문 수나 단계는 고정하지 않는다.

- 사용자와 사용 장면, 현재 방식과 어려움, 판단 기준과 사례, 자료의 의미와 신뢰 범위, 예외, 성공 기준, 이번에 제외할 범위를 살펴본다. 이미 답이 있거나 현재 판단에 영향이 없으면 묻지 않는다. 이 목록은 빠짐없이 질문하라는 체크리스트가 아니다.
- 각 후보에 왜 묻는지(알게 될 업무 사실), 답에 따라 바뀌는 판단(범위·화면·규칙·검증 등), 확인 대상과 관찰 근거를 붙인다. 지금 필요한 것과 나중에 확인할 것을 구분한다.
- 출발 방향을 바꿀 질문과 다른 질문의 전제가 되는 것을 우선한다. 사소 → 깊음의 고정 순서로 재정렬하지 않는다. 실제 전달할 질문은 상대가 답할 수 있는 구체적인 하나로 좁힌다. 상황별 상대의 응답 방식은 SITUATION을 참고한다.
- 업무 사실·판단 기준은 파트너, 범위·설계 선택은 사용자, 자료에서 확인 가능한 사실은 로컬 자료, 환경은 Helper로 보낸다. 파트너는 기술 선택과 해결 설계를 대신 정하는 사람이 아니다.
- 일반 지식으로 놓친 관점을 보완할 수 있으나 해당 팀의 사실로 쓰지 않는다. “보통 이렇다는데 맞죠?”로 유도하기보다 실제 방식과 사례를 묻는다. 웹 조사가 필요하면 research의 출처 판단과 사용자 허락을 먼저 거친다.

## 예: 관찰에서 질문으로
자료에서 같은 유형에 서로 다른 처리 기록을 봤다면 “이 두 사례는 어떤 조건 때문에 처리가 달라졌나요?”라고 묻는다. 차이의 이유가 확인되면 분기 규칙이나 확인할 예외를 정할 수 있다. 일부 사례만으로 전체 규칙을 만들지 않는다.

## 받은 답과 추가 질문
사용자가 독자적으로 물은 질문도 동일하게 받는다. 원문을 보존하고 답이 실제 쟁점을 해결하는지 판단한다. 답이 모호하거나 충돌하면 필요한 후속 질문만 만든다. 범위에서 제외했거나 가정으로 수용한 쟁점은 그 이유·후속 확인을 남긴다. 질문이 모두 답변됨과 setup 준비 완료는 다르며 완료 기준은 setup SKILL에 있다.
