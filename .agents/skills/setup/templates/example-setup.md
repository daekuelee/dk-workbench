# setup — 팀 IT 문의 티켓 현황 화면

결론: 팀장은 밀리는 IT 문의를 한눈에 보고 싶어 하지만, 무엇을 "밀림"으로 볼지와 언제 어떤 기기로 볼지는 아직 비어 있다.
정할 것: 아키텍처 안 (추천: 1안, 집계를 API 로 따로 확인할 수 있어 숫자 검증이 쉽다)

## 상황
팀장은 팀의 IT 문의 처리가 늦어지고 있다고 느낀다. 지금은 티켓 목록을 직접 훑어서 판단하는 것으로 보인다(모름, 확인 필요). README 에는 "한눈에" 라는 말만 있고, 밀림의 기준, 보는 시점, 담당자별로 볼지는 없다. 숨어 있을 것은 팀장이 머릿속에 가진 "밀렸다"의 기준이다.

```text
팀장 ──(언제? 어떤 기기?)──► 티켓 목록을 훑음 ──► 밀림을 늦게 앎
                                   ▲
                       "밀렸다"의 기준 (상태? 경과 일수? 우선순위?)
```

| 자료 | 직접 센 값 | 명령 |
|---|---|---|

## 아키텍처 안
| 안 | 구조 한 줄 | 왜 | 위험 | 첫 동작본까지 |
|---|---|---|---|---|
| 1안 | FastAPI 가 시작할 때 CSV 를 읽고, 집계 API 와 HTML 한 장을 준다 | 집계를 API 로 따로 확인할 수 있다 | 설치가 막힐 수 있다 | 20~25분 |
| 2안 | 표준 라이브러리 http.server 가 HTML 을 서버에서 만든다 | 설치가 없다 | 화면과 집계가 한 곳에 얽힌다 | 20~30분 |

추천: 1안. 숫자가 맞는지 API 로 바로 대조할 수 있다. 설치가 막히면 2안으로 간다.

## 파트너에게 물을 질문
| 순서 | 질문 | 왜 묻나 (채울 칸, 답에 따라 바뀌는 것) | 깊이 |
|---|---|---|---|
| 1 | 이 화면은 팀장님이 직접 보시나요? | 실제 사용자. 여러 명이면 화면 단위가 바뀐다 | 사소 |
| 2 | 보통 언제, 어떤 기기로 보시나요? | 쓰는 장면. 한 화면 크기와 갱신 시점이 정해진다 | 사소 |
| 3 | 최근에 "밀렸다" 고 느끼신 일이 있었나요? | 숨어 있을 방식의 실마리. 기준의 출처가 된다 | 중간 |
| 4 | 어떤 티켓을 밀린 것으로 보세요? 상태와 경과 일수 중 무엇으로 보시나요? | 숨어 있을 방식. 핵심 집계 규칙이 정해진다 | 중간 |
| 5 | 우선순위에 따라 기준이 달라지나요? | 기준의 예외. 규칙이 하나인지 둘인지 바뀐다 | 깊음 |
| 6 | 담당자별로 보고 싶으신가요, 전체 숫자면 되나요? | 화면 구성. 묶는 단위가 바뀐다 | 중간 |
| 7 | 이 자료는 어디서 뽑으신 건가요? 믿기 어려운 칸이 있나요? | 자료 믿음. 정리 규칙과 기준일이 바뀐다 | 중간 |
| 8 | 이번에 안 해도 되는 건 무엇인가요? | 하지 않는 것. 범위가 줄어든다 | 사소 |

## 검증 방식 초안
S0 에서 CSV 를 직접 집계한 값을 기대값으로 적고, API 값과 verify.sh 로 비교한다. 밀림 기준이 정해지면 그 기준으로 다시 센다. 기대값의 출처는 data/tickets.csv 를 표준 라이브러리로 센 결과다.
